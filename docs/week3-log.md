# Week 3 — Master Data Management: Outcome & Skills Log

## What was built
- A synthetic second "source system" (vendor records) generated by sampling 300
  active companies and deliberately corrupting their names (abbreviations, casing,
  punctuation, typos, whitespace) — simulating how the same real-world entity gets
  recorded inconsistently across separate business systems with no shared key.
- A two-stage match/merge pipeline: postcode-based blocking to narrow the search
  space, followed by fuzzy name scoring (rapidfuzz, token_sort_ratio) within each
  block — the standard technique for making entity resolution computationally
  tractable at scale.
- Matcher accuracy validated against known ground truth (the true company number
  was tracked separately from what the matcher could see), rather than assumed.
- A golden_records table (294 records) built from confident matches only —
  abstentions routed to manual review rather than force-matched.

## Evaluation findings (tested deliberately, not assumed)
- An early accuracy metric conflated two distinct failure modes — a wrong
  confident match (false positive) and a correct-but-unconfident abstention — into
  one boolean. Caught by manually inspecting a borderline case (score 76.5,
  just below the 80 threshold) that looked more "right" than "wrong." Rebuilt the
  metric to separate precision (of asserted matches) from recall (coverage),
  which is the correct way to evaluate a matcher.
- Final result: 100% precision (0 false positives across 294 asserted matches),
  6 records abstained below threshold, of which 5 would have been correct had the
  threshold been lower — a measured, explicit precision/recall trade-off rather
  than an arbitrary threshold choice.

## Real debugging encountered
- The `companies` dbt model was a view by default, meaning it re-executed its
  underlying S3 read (with dbt's own credentials) every time it was queried. A
  separate Python script using a plain DuckDB connection had no access to those
  credentials, and DuckDB silently defaulted to assuming real AWS S3 rather than
  MinIO. Fixed by materializing `companies` as a physical table — also a
  legitimate real-world modeling decision (views vs. tables) beyond just a bug fix.
